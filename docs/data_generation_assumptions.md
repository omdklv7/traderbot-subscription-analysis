# Допущения при генерации синтетических данных TraderBot

## 1. Назначение документа

Документ описывает правила формирования синтетического датасета TraderBot.

**Данные искусственные.** количество пользователей, конверсии, вероятности поведения и рассчитанные метрики не являются реальными результатами деятельности TraderBot. Их нельзя использовать для утверждений об эффективности продукта без проверки на настоящих данных.

## 2. Источники параметров и статус допущений

Разделяем два типа информации:

- **Сведения о продукте:** параметры, полученные из описания TraderBot, пользовательского опыта и интервью в рамках проекта. Они не подтверждены независимым аудитом.
- **Синтетические допущения:** вероятности, диапазоны времени и упрощения, выбранные специально для генерации учебного датасета.

## 3. Общие параметры датасета

| Параметр | Значение |
|---|---|
| Число зарегистрированных пользователей | 10 000 |
| Базовый генератор случайных чисел | `SEED = 42` |
| Регистрации | С 01.01.2025 по 30.06.2026 включительно |
| Конец наблюдения | `2026-10-01 00:00:00 UTC`, исключая саму границу |
| Часовой пояс | UTC (`TIMESTAMPTZ`) |
| Денежная единица | USD |
| Формат выгрузки | 10 CSV-файлов в `data/synthetic/` |
| Основной генератор | `python/generate_data.py` |
| Независимый валидатор | `python/validate_data.py` |

## 4. Пользователи — `users`

- Первоначальный выбор модели: **70% подписка**, **30% лицензия**.
- Источник регистрации: **website — 50%**, **telegram — 25%**, **referral — 15%**, **ads — 10%**.
- Способ авторизации: **email — 50%**, **telegram — 50%**.
- Момент регистрации равномерно случайно выбирается внутри заданного временного интервала.
- Поле `initial_model` — **первоначальное предпочтение**, а не факт покупки.

## 5. Создание подписок — `subscriptions`

- Подписку могут создать только пользователи, выбравшие `initial_model = 'subscription'`.
- Вероятность создания — **80%**.
- Задержка после регистрации — от **0 до 30 полных дней** и дополнительно от **0 до 23 часов**.
- Один пользователь имеет не более одной записи в `subscriptions`.
- Создание записи само по себе не означает оплаты или технической активации.

## 6. Первые платежи — `payments`

- Для каждой созданной подписки формируется одна первая попытка оплаты.
- Первая попытка происходит спустя **0–14 дней** плюс **0–23 часа** после создания подписки.
- Результат: **78% `confirmed`**, **22% `failed`**.
- Подтверждение успешной первой оплаты занимает **1–180 минут**.
- Способ оплаты: **СБП — 65%**, **криптовалюта — 35%**.
- Сумма каждого платежа по подписке — **$50**.
- Для `failed` и `pending` поле `confirmed_at` пустое.
- Код допускает `pending`, если подтверждение вышло за конец наблюдения; в текущем наборе первые попытки происходят слишком рано для такого случая.
- Повторные попытки после первой неуспешной оплаты **не моделируются**. Для дальнейших продлений отдельно не генерируются неуспешные попытки списания.

## 7. Оплаченные периоды — `subscription_periods`

- Один подтверждённый платёж соответствует ровно одному оплаченному периоду той же подписки.
- Первый период начинается в момент подтверждения первой оплаты.
- Продолжительность — **один календарный месяц**.
- При непрерывном продлении новый период начинается ровно в момент окончания предыдущего.
- При реактивации допускается разрыв между периодами; пересечение запрещено.
- `period_no` нумеруется последовательно внутри подписки.
- `canceled_at` остаётся пустым: досрочные отмены не симулируются.
- Период может закончиться после 30.09.2026, если его оплата подтверждена до конца наблюдения.
- Добавление календарного месяца реализовано через ограничение номера дня последним днём следующего месяца. Например, после перехода **31 января → 28 февраля** последующее добавление месяца даст **28 марта**: исходный день месяца не восстанавливается.

## 8. Первичная техническая активация — `activations`

- Активация формируется только после успешной первой оплаты.
- Запрос на активацию: **0–5 минут** после подтверждения оплаты.
- Вероятность завершения: **99% `completed`**, **1% `failed`**.
- Для **успешных** активаций длительность распределена следующим образом:

| Время подключения | Доля успешных активаций |
|---|---:|
| 15–30 минут | 85% |
| 31–240 минут | 10% |
| 241–1 440 минут | 5% |

- Для неуспешной активации `completed_at` отсутствует.
- Повторная техническая активация при возвращении после просрочки не создаётся.
- **Ограничение:** платный период начинается при подтверждении оплаты, в том числе если техническая активация ещё не завершена или завершилась неуспешно.

## 9. Изменения настроек — `setting_changes`

- Настройки меняют только успешно активированные подписчики.
- Вероятность хотя бы одного изменения в **первом оплаченном периоде** — **35%**.
- Число изменений среди изменявших: **1 — 70%**, **2 — 23%**, **3 — 7%**.
- Начальные значения: `risk_level = medium`, `trading_mode = balanced`.
- Возможные риски: `low`, `medium`, `high`; режимы: `conservative`, `balanced`, `aggressive`.
- Каждая новая комбинация отличается от предыдущей минимум одним параметром.
- Изменения происходят после завершения активации и до окончания первого оплаченного периода.
- События изменения настроек во втором и последующих периодах не формируются.

## 10. Инциденты — `incidents` и `incident_impacts`

Генерируется **ровно 70 технических инцидентов** с января 2025 года до конца сентября 2026 года. Начало инцидента не попадает в последние двое суток наблюдения; все сгенерированные инциденты завершены.

| Критичность | Доля инцидентов | Продолжительность | Вероятность затронуть подходящую подписку |
|---|---:|---|---:|
| `low` | 50% | 10–60 минут | 5% |
| `medium` | 30% | 30–180 минут | 15% |
| `high` | 15% | 60–480 минут | 35% |
| `critical` | 5% | 120–1 440 минут | 70% |

Категории: `trading_engine`, `vps`, `connectivity`, `dashboard`, `updates`.

Воздействие создаётся, только если инцидент пересёкся с **оплаченным доступом после успешной активации**. Для пары «инцидент — подписка» допускается только одно воздействие. `affected_at` — начало наблюдаемого пересечения, `restored_at` — время устранения инцидента (оно может быть позже окончания конкретного оплаченного периода). После расширения истории подписок воздействия пересчитываются.

## 11. Первое продление

Для подписок с завершившимся первым оплаченным периодом вероятность первого непрерывного продления задаётся следующим образом:

| Фактор | Изменение вероятности |
|---|---:|
| Базовое значение при успешной активации | 68% |
| Длительность активации 31–240 минут | −5 п. п. |
| Длительность активации свыше 240 минут | −12 п. п. |
| Воздействие технического инцидента | −10 п. п. |
| Изменение настроек | +8 п. п. |
| Неуспешная активация | Отдельная вероятность 4% |

- Корректировки длительности активации взаимоисключающие; остальные факторы могут суммироваться.
- Итоговая вероятность ограничивается диапазоном **2–95%**.
- Подтверждение оплаты непрерывного первого продления моделируется за **1–72 часа** до конца первого периода, инициирование — ещё за **1–120 минут** до подтверждения.
- Первым продлением считается лишь второй период, начавшийся **без перерыва**. Более поздний второй период — реактивация, а не первое продление.

Эти коэффициенты **заложены генератором** и не являются результатом статистического исследования реальных клиентов.

## 12. Третьи и последующие непрерывные периоды

- После успешного первого продления вероятность каждого следующего непрерывного продления — **78%**.
- При отказе в продлении непрерывная цепочка прекращается.
- Подтверждение оплаты — за **1–48 часов** до конца текущего периода, инициирование — ещё за **1–120 минут** до подтверждения.
- Сохраняются цена $50 и распределение способов оплаты 65/35.
- Последующие продления генерируются, только если текущий период завершился до границы наблюдения.
- Сезонность, индивидуальная склонность к продлению и неуспешные попытки регулярной оплаты не моделируются.

## 13. Реактивации и продления после возвращения

- Рассматриваются только ранее оплатившие подписчики с **успешной первоначальной активацией**.
- Реактивация рассматривается, если после последнего оплаченного периода до конца наблюдения остаётся **более 7 дней**.
- Вероятность решения вернуться — **20%**.
- Моделируемый перерыв: **7–90 дней** плюс **0–23 часа**.
- Если рассчитанная дата возвращения находится за пределами наблюдения, реактивация не записывается.
- После новой подтверждённой оплаты создаётся очередной период; техническая активация повторно не выполняется, настройки считаются сохранёнными.
- В данном алгоритме моделируется **не более одной реактивации на подписку**.
- Вероятность каждого непрерывного продления **после возвращения — 78%**; оплата за 1–48 часов до конца периода.

**Observed Reactivation Rate** — доля зафиксированных возвращений среди подписок, признанных подходящими для моделирования реактивации.

## 14. Обращения в поддержку

Обращения привязываются к уже созданным событиям, а не распределяются независимо.

| Основание для обращения | Вероятность создания тикета |
|---|---:|
| Неуспешная активация | 70% |
| Успешная активация | 8% |
| Неуспешный платёж | 20% |
| Воздействие технического инцидента | 22% |
| Общее обращение после успешной активации | 12% |

- У одной подписки может быть несколько обращений.
- Категории: `activation`, `payment`, `technical`, `general`.
- Техническое обращение возникает во время зарегистрированного воздействия; общее — в первом оплаченном периоде.
- Время закрытия задаётся от **1 часа** до **48 часов 59 минут** после открытия.
- Если срок закрытия наступает после конца наблюдения, `closed_at` остаётся пустым.
- После добавления продлений и реактиваций обращения генерируются заново на основании итоговых событий.

## 15. Покупки лицензий — `license_purchases`

- Покупка возможна только для пользователей с `initial_model = 'license'`.
- Вероятность покупки — **70%**.
- Среди покупателей **85%** совершают покупку в интервале **0–30 дней** после регистрации; остальные **15%** — в интервале **31–90 дней**.
- Цена каждой сгенерированной лицензии — **$550** (упрощение относительно минимальной известной цены).
- Не более одной покупки на пользователя.
- Покупки после границы наблюдения не записываются.

## 16. Определения метрик и корректность сравнения

| Метрика | Интерпретация в датасете |
|---|---|
| **30-day Payment Conversion** | Доля зарегистрированных пользователей выбранной модели, оплативших впервые **ранее** чем через 30 дней после регистрации |
| **First Renewal Rate** | Непрерывные вторые оплаченные периоды / первые периоды, завершившиеся до конца наблюдения |
| **Subsequent Renewal Rate** | Успешные последующие продления / завершившиеся возможности продления в непрерывных цепочках после второго периода |
| **Observed Reactivation Rate** | Зафиксированные реактивации / подписки, подходящие под реализованную процедуру оценки возвращения |
| **Post-reactivation Renewal Rate** | Успешные непрерывные продления после возвращения / завершившиеся возможности такого продления |
| **MRR** | При выбранном определении: число подписок с действующим оплаченным доступом на дату × $50; не равно сумме поступлений за месяц |
| **Денежные поступления** | Подтверждённые платежи по подпискам и покупки лицензий; депозит у брокера исключён |

В текущем наборе всем пользователям доступно полное 30-дневное окно наблюдения, поскольку регистрации закончились 30.06.2026, а наблюдение — 30.09.2026.

## 17. Контроль качества, ограничения и воспроизводимость

Независимый `python/validate_data.py` читает готовые CSV и проверяет первичные и внешние ключи, дополнительные ограничения `UNIQUE`, связь подтверждённых платежей с периодами, хронологию регистрации, оплат, активаций, инцидентов, изменений настроек, тикетов и покупок, отсутствие пересечений периодов, а также отдельные аналитические окна.

**Ограничения модели:**

1. Вероятности подобраны для учебного анализа, а не оценены по реальным событиям.
2. Досрочные отмены (`canceled_at`) и многократные циклы реактивации отсутствуют.
3. Не моделируются повторные попытки первоначальной оплаты и полноценная история неуспешных продлений.
4. Изменения настроек ограничены первым оплаченным периодом.
5. Инциденты имеют упрощённую общую модель вероятности воздействия; нет детализации по инфраструктурным группам.
6. Нет торговых результатов, брокерских депозитов, операционных расходов и стоимости поддержки/VPS.
7. Подписка может быть оплаченной при неуспешной технической активации; для отдельных метрик требуется различать **оплаченный доступ** и **фактическую работоспособность сервиса**.
8. Данные обладают правым цензурированием для событий и показателей, требующих наблюдения после 30.09.2026.
9. Успешное выполнение валидатора подтверждает только реализованные проверки, а не полное соответствие производственным данным или всем возможным ограничениям PostgreSQL.
